## What changed

Two integration plans under `docs/blueprints-next/_research/`. **No code.** Both are proposals
that name their own open decisions rather than settling them.

### `central-kb-connectivity.md`

How `devx-commerce/retail-os-central-kb` reaches a builder lane through the existing
`knowledge -> context` edge.

Measured on the KB (2026-09-22): 129 files — 31 features, 17 domain, 23 integrations, 13 defects,
12 architecture, 7 playbooks. `standards/` holds only `_PROMOTION.md`, which is correct: it grows
from real runs, never from a bulk import.

Measured on the harness: `scan` and `plan` are stubs (`merges zero questions`,
`fixed draft, not per-task`), `knowledge` is `partial`, and no `KnowledgeStore` reads an external
repo. A lane receives only the task string — observed directly, a builder lane on a real POSX task
replied *"you haven't provided the current contents, I'll assume a basic structure"* and invented
a file.

So the gap is not retrieval quality. It is 96 curated files sitting unread while lanes start from
zero.

Proposes: shallow git clone into `$FLEET_STATE/kb/`, a `CentralKbStore` implementing the existing
`KnowledgeStore` trait, git blob SHA as `source_digest` and commit SHA as `revision` (no new
provenance machinery), `kind` decided by **path not front-matter** so a file cannot promote itself
into authority, and lexical retrieval via the already-present `tantivy` before anything semantic.

Keeps the denominator rule: a retrieval that examined zero sources **refuses**, rather than
proceeding with an uninformed lane — which is today's behaviour and the reason lanes invent files.

### `learning-promotion-loop.md`

How a verified failure becomes a rule that blocks a merge, through
`verify -> candidate -> offline -> knowledge -> standards`.

Records that the chain is designed and unbuilt: `candidate` and `knowledge` are `partial`,
**`offline` is `greenfield`** — and `offline` is the node that stops one failure becoming a rule.

Four gates: the failure is real (`{checked,total}`), it has a signature and a regression fixture,
a paired trial says the lesson helps, and a human grants authority via
`standards/_PROMOTION.md`. Proposes a first increment that does not build all four — human review
occupies the `offline` slot explicitly, and one rule (`DEF-0001`, money steps without
`compensate`) goes end to end, warn-only before blocking.

## Known blockers and unverified claims

- **`FD-8` blocks the KB plan**, and this is easy to miss. A POSX repo runs `npm run test:unit`,
  passes 671 tests, and fleet reports `Unparseable` — the denominator parsers are libtest-shaped.
  Until a Node repo can pass a gate, a perfectly-contextualised lane still ends in refusal, so the
  value of KB connectivity is not observable. Order: **FD-8 → KB connectivity → promotion loop.**
- The front-matter scope schema needs a **KB-side change** (`repos:` / `clients:`), so it is a
  coordination item, not a fleet-only one.
- `offline` being greenfield is the largest single piece of unestimated work in the promotion loop.
- Nothing in either document has been prototyped. The measurements of the KB and of the harness
  are real; the designs are not yet tested against anything.
